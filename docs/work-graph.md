# WorkGraph 使用说明

默认工作视图读取当前仓库的 `.workgraph/state.json`（兼容旧 `.workgraph.json`） 和 HEAD 最近 300 条实际提交。工作状态由记录明确维护，不能从提交数量推断完成、验证通过或用户接受。

工作列表默认每项一行，只显示标题、状态和记录更新时间。行首箭头展开具体子工作与成果；没有子项时不显示箭头。点击标题打开同一个底部详情面板，上方列表保留筛选、展开和滚动位置。底部「进展」页展示摘要、下一步、成果和问题，「代码依据」页展示关联提交及实际差异。面板可收起，也可拖动分隔条调整高度；分隔条支持方向键、Home 和 End。

可按工作状态筛选，或搜索工作标题、ID、摘要、下一步、成果、问题以及关联提交的标题和 SHA。命中子项时保留父级上下文并展开相关层级，提交仍只在详情中展示。详情中的关联提交数量只统计本次加载范围。未提交文件在详情中单独列出，不归属到当前选中的工作项。刷新更新记录与 Git 数据；Git 历史入口保留原有操作。

筛选反馈区分匹配数量与仓库总计，仅为保留父级路径而显示的项目标注为「所属工作」。

父级详情汇总本层及子孙明确记录的成果并标明来源，不受当前搜索或筛选影响；相同来源内去重，不跨来源合并。

## 配置工作记录

### 按用户要求更新

对外只有 `workgraph` skill。用户要求更新地图时，当前聊天的 Agent 通过 CLI `context` 收集证据，结合已确认的聊天信息整理候选，再通过 `save` 校验与保存。代码根据 `.workgraph/state.json` 是否存在自动路由首次建立或增量更新；只有旧 `.workgraph.json` 时，以旧记录为基线迁移。空地图也是有效的已有地图，不会反复初始化。记录损坏或版本不支持时报错并保留原文件。

地图以项目目标组织工作与成果，当前沿用最多三层的父子工作结构。目标可作为顶层工作表达，子工作和成果关联其下；不将聊天或每次提交逐条变成工作。没有代码变化时，用户确认的目标、问题和下一步仍可更新。实现完成、验证通过和用户验收分别表述。Agent 自主重组范围待实际使用后再收敛，当前保留已有 ID 和有效依据。

CLI `status` 与 `open` 只读取或展示，不启动分析。`context` 自动在 `.workgraph/runtime/` 下创建唯一请求目录，返回材料与候选路径；材料不是永久工作记录。`save` 需要本次材料及候选，拒绝材料收集后的代码或记录变化，防止旧结果覆盖新状态。完整流程见 [skill](../skills/workgraph/SKILL.md)。

插件保留「更新工作地图」按钮及 `git_graph_work_analyze`，默认 `mode: auto`。这一兼容入口调用 `codex exec --sandbox read-only --output-schema ...`，使用本机认证与模型配置，不能读取发起请求的聊天正文。Windows 默认通过 `where.exe codex.exe` 查找程序，也可设置 `WORKGRAPH_CODEX_PATH`，不支持 `.cmd`、`.bat` 或 `.ps1`。Codex 子进程超时为 10 分钟，准备与保存时间另计。

两条路径共用有界证据收集、工作项校验、跨进程锁、保存前复核和原子保存。材料最多 64 KiB，单份文档摘录最多 8 KiB，已有地图另行传入；截断和未读取内容不能作为完成依据。存在 CodeGraph 时优先使用已有索引，不自动创建索引。

更新时先核实历史基线，只提供基线之后的新提交，并检查提交净变化、当前未提交文件和上次分析时的未提交路径。缺少路径基线、覆盖不完整或历史不连续时，标注原因并回退到有界项目地图。增量结果只包含修改、新增工作及明确保留的 ID；未变化项保留原内容与更新时间。

当前 CLI 路径有一项已知限制：材料写入 `context.json` 时未保留内部的未提交路径基线，因此后续更新可能因缺少基线而回退到有界项目地图。已有工作仍会保留，但不能保证每次仅收集新增变化。插件直接调用本机 Codex 的分析路径不经过这一序列化步骤。

服务不再执行自动变化检测、后台分析或失败重试，即使旧记录包含 `automation.enabled: true`。面板每 5 秒读取轻量状态，空闲时每 15 秒刷新记录和 Git 数据，以读取其他进程保存的结果；这类读取不调用模型。「刷新」只读取，「更新工作地图」才请求分析。

保存阶段耗时记录于 `.workgraph/runtime/last-analysis.json`，只保留最近一次摘要，不包含提示词、项目正文、模型输出或错误正文。CLI 模式下，Agent 在 `context` 与 `save` 之间的思考时间不计入保存耗时；插件分析入口显示其本机 Codex 执行阶段。诊断文件保存失败不影响有效工作记录。

输出无效、已有工作项丢失或分析期间代码和记录变化时，保留上一份有效记录。Git 管理由插件界面提供，skill 不执行 Git 写操作。

### 仓库内存储

```text
.workgraph/
├─ state.json        # version、works、automation、analysis，一次原子保存
├─ .gitignore        # 忽略运行文件与临时结果
└─ runtime/          # 分析材料、候选、锁及最近一次计时摘要，不纳入 Git
```

`state.json` 的 `analysis` 记录上次分析的 HEAD、分支、代码指纹、时间和范围，并保存有界的未提交路径基线；不保存旧工作区正文，不能据此还原旧的逐行差异。路径基线与工作项一起原子保存，失败分析不会推进基线；接近记录大小上限时优先保留工作项，下次分析安全回退。`automation.enabled` 仅为兼容旧格式保留，新保存值为 `false`；服务不根据此字段启动分析。工作记录建议纳入 Git。不同 Worktree 保存各自的记录；裸仓库不支持初始化。

首次读取优先使用新目录，没有新记录时兼容读取根目录 `.workgraph.json`。初始化以旧记录为起点并保留工作项 ID，迁移后保留旧文件，新记录优先。当前不提供面板内编辑工作项的表单。

### 文件格式

以下是 `state.json` 中工作数据的最小结构；通常由内置 Skill 和本地服务维护，无需手动创建。示例省略服务维护的 `automation` 和 `analysis` 字段：

```json
{
  "version": 1,
  "works": [
    {
      "id": "WG-DOCS",
      "title": "更新使用文档",
      "status": "进行中",
      "next": "核对说明与当前实现",
      "summary": "补充工作记录配置和数据边界。",
      "commits": []
    },
    {
      "id": "WG-DOCS-SCOPE",
      "parentId": "WG-DOCS",
      "kind": "outcome",
      "title": "明确工作记录的数据边界",
      "status": "已完成",
      "summary": "已写明读取范围与归属规则，尚未由用户验收。",
      "outcomes": ["说明 HEAD 历史的读取范围"],
      "issues": ["后续需随实现核对"],
      "commits": []
    }
  ]
}
```

| 字段 | 要求 |
| --- | --- |
| `version` | 必须为数字 `1` |
| `works` | 必填数组，父项和子项合计最多 100 个，可为空 |
| `id` | 唯一标识，1–40 个字符，以大写英文字母开头，其余只能是大写英文字母、数字或连字符 |
| `title` | 必填非空白字符串，最多 160 个字符 |
| `status` | 必须是 `进行中`、`已完成`、`已搁置`、`待开始` 之一 |
| `commits` | 必填数组，可为空，单项最多 1000 个；填写完整提交 SHA，同一 SHA 不能重复填写或分配给多个工作项 |
| `next`、`summary` | 可选字符串，各最多 1000 个字符 |
| `parentId` | 可选，填写已有工作项 ID；省略时为顶层动线。拒绝缺失父项、循环引用，最多支持三层 |
| `kind` | 可选，`work`（默认）为工作，`outcome` 为成果；只改变展示类型，不证明完成或验收 |
| `updatedAt` | 可选，实际维护记录时填写 UTC ISO 时间，如 `2026-10-28T08:00:00.000Z`，也接受不带毫秒的形式；界面按北京时间展示，缺失显示 `—`，不使用提交时间补齐 |
| `outcomes`、`issues` | 可选字符串数组，各最多 20 项；每项非空白且最多 1000 个字符，分别记录成果与问题／边界 |

文件必须是普通文件，不能是符号链接，大小不能超过 256 KiB。格式错误会阻止工作视图加载。不要使用 `UNASSIGNED` 作为自定义工作项 ID；它用于显示待归类提交。

以上可选字段扩展现有 `version: 1`；旧的平面工作记录仍可读取。工作项拒绝未知字段。子工作应依据明确目标与完成条件整理，不能仅为形成树状结构创建记录，也不能因子项完成就自动修改父项状态。

建议将记录与代码一起提交。界面读取当前工作区的文件，尚未提交的记录修改也会在刷新后显示。不同 Worktree 读取各自工作区的记录；裸仓库不读取此文件。

## 关联提交

关联方式有两种：工作记录中的完整提交 SHA，以及提交正文中的 `Work-Item: WG-ID` 标识。显式 SHA 优先；没有明确关联的提交归入「待归类提交」；该合成入口不计入工作进度或待开始筛选。未提交文件单独显示，不推断工作归属。历史重写后需要核对并更新 SHA；本版不自动修复关联。

父项详情可以汇总后代的明确关联，并标注来自哪个子项；子项不会继承父项提交。父项已有提交无需强行重新分配给子项。没有单独关联时，子项「代码依据」明确显示暂无关联。

例如，为上面的 `WG-DOCS` 工作项创建提交时，可在提交消息正文中另起一行写入 `Work-Item: WG-DOCS`。没有显式 SHA 关联时，正文中必须恰好有一行符合格式的标识，且 ID 已存在于工作记录中；多个标识或未知 ID 都不会建立归属。仅在提交标题中写入标识不会生效。

## 数据范围与限制

工作轨道表示同一工作的成果归属，不表示 Git 父子关系。历史提交的工作归类依据本次整理，Git 日期与差异来自仓库事实。工作记录和代码一起提交，其他仓库未配置记录时只显示未关联历史。

本版只读取当前 HEAD 可达历史，超过 300 条时提示截断；其他分支和 worktree 的完整历史仍在 Git 模式查看。分析仅在用户要求时执行；没有后台自动维护、自动提交、恢复点或自动验收。界面读取失败会显示错误，不回退到演示数据。

原型代码保留用于交互测试，已不作为默认首页。旧原型说明见[原型记录](work-prototype.md)。
