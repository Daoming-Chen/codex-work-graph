# WorkGraph 使用说明

默认工作视图优先读取当前仓库的 `.workgraph/state.json`（兼容旧 `.workgraph.json`）和 HEAD 最近 300 条实际提交。工作状态由记录明确维护，不能从提交数量推断完成、验证通过或用户接受。

工作列表默认每项一行，只显示标题、状态和记录更新时间。行首箭头展开具体子工作与成果；没有子项时不显示箭头。点击标题打开同一个底部详情面板，上方列表保留筛选、展开和滚动位置。底部「进展」页展示摘要、下一步、成果和问题，「代码依据」页展示关联提交及实际差异。面板可收起，也可拖动分隔条调整高度；分隔条支持方向键、Home 和 End。

可按工作状态筛选，或搜索工作标题、ID、摘要、下一步、成果、问题以及关联提交的标题和 SHA。命中子项时保留父级上下文并展开相关层级，提交仍只在详情中展示。详情中的关联提交数量只统计本次加载范围。未提交文件在详情中单独列出，不归属到当前选中的工作项。刷新更新记录与 Git 数据；Git 历史入口保留原有操作。

## 配置工作记录

### 初始化与自动维护

首次点击「初始化当前仓库」，或通过内置 `workgraph-init` Skill 调用 `workgraph_work_analyze`（`mode: initialize`）。本地服务加载初始化 Skill，调用 `codex exec --sandbox read-only --output-schema ...` 分析项目，再校验并保存结果。服务使用本机 Codex 的现有认证和模型配置，不替换登录信息。Windows 默认通过 `where.exe codex.exe` 查找程序，也可设置 `WORKGRAPH_CODEX_PATH`。不支持将 `.cmd`、`.bat` 或 `.ps1` 作为此变量的目标。

服务先收集项目约定、入口、计划与需求文档摘录，以及文件清单、提交和未提交改动统计，形成最多 64 KiB 的分析材料。单份文档摘录最多 8 KiB，材料明确标注截断、省略和未读取的源码。初始材料跳过归档、二进制文件、依赖及构建目录；模型先建立工作地图，再针对证据缺口补读相关章节或源码。已有工作项另行完整传入，不计入材料的 64 KiB 限额。存在 CodeGraph 索引时，进一步理解或定位代码优先使用索引，不自动创建索引。

面板显示当前阶段和已用时间，包括准备、计算变更指纹、收集分析材料、Codex 分析、结果校验、变化复核和保存。Codex 分析阶段包含子进程启动、模型调用及按需读取，当前不进一步拆分，也不显示估算百分比。分析完成后显示上次成功耗时。

每次分析的阶段耗时保存在 `.workgraph/runtime/last-analysis.json`，只保留最近一次摘要，重新打开项目后可读取。摘要包含执行模式、开始和结束时间、总耗时、各阶段耗时及失败阶段，不包含提示词、项目正文、模型输出或错误正文。诊断文件保存失败不影响已经保存的有效工作记录。

初始化成功会启用自动维护。服务每 15 秒检查 HEAD、分支、暂存与未暂存差异，以及未跟踪文件内容；忽略 `.workgraph/` 和旧记录文件。检测到变化稳定至少 30 秒后，加载 `workgraph-update` Skill 执行增量分析。打开已有项目时恢复检测，不需要再次初始化。服务关闭期间不分析；当前没有常驻系统服务或聊天阶段结束事件接入。

面板前台每 5 秒读取轻量分析状态，分析结束时刷新结果，空闲时每 15 秒刷新完整记录与 Git 数据，以便读取其他进程保存的变化。状态查询和服务定时检测共享检查间隔及正在执行的扫描，避免重复计算指纹；手动分析仍执行新的基线计算与保存前复核。

更新时先核实历史基线，只提供基线之后的新提交，并重点检查提交净变化、当前未提交文件和上次分析时的未提交路径。这样可以核对改动撤销、未跟踪文件删除等同一 HEAD 下的变化。旧记录缺少路径基线、覆盖不完整或提交历史不再连续时，明确标注原因并回退到有界项目地图。模型只返回修改、新增的工作项及明确保留的 ID，服务校验覆盖后合并成完整记录；未变化项保留原内容和更新时间。

「刷新」重新读取记录和 Git 数据；「更新分析」立即调度一次分析，也用于失败后重试。自动维护已经启用时，刷新或重新打开面板会恢复该仓库的变化检测。分析使用本机模型额度。Codex 子进程的超时为 10 分钟，本地准备、材料收集与保存前复核的耗时另计。同一变化失败后间隔至少 60 秒重试，累计三次后停止，等待手动重试或新的代码变化。

分析期间代码或工作记录变化、输出无效、已有工作项丢失时，不覆盖上一份记录。文件锁避免多个服务同时分析同一工作区，保存采用临时文件和原子替换。初始化未成功时不会启用自动维护。工作项状态不能根据提交数量推断，未执行的验证不能写成通过。

### 仓库内存储

```text
.workgraph/
├─ state.json        # version、works、automation、analysis，一次原子保存
├─ .gitignore        # 忽略运行文件与临时结果
└─ runtime/          # 本地分析锁及最近一次计时摘要，不纳入 Git
```

`state.json` 的 `analysis` 记录上次分析的 HEAD、分支、代码指纹、时间和范围，并保存有界的未提交路径基线；不保存旧工作区正文，不能据此还原旧的逐行差异。路径基线与工作项一起原子保存，失败分析不会推进基线；接近记录大小上限时优先保留工作项，下次分析安全回退。`automation.enabled` 记录是否启用自动维护。工作记录建议纳入 Git。不同 Worktree 保存各自的记录；裸仓库不支持初始化。

首次读取优先使用新目录，没有新记录时兼容读取根目录 `.workgraph.json`。初始化以旧记录为起点并保留工作项 ID，迁移后保留旧文件，新记录优先。当前不提供面板内编辑工作项的表单。

### 文件格式

以下是 `state.json` 中工作数据的最小结构；通常由内置 Skill 和本地服务维护，无需手动创建。示例省略服务维护的 `automation` 和 `analysis` 字段：

```json
{
  "version": 1,
  "works": [
    {
      "id": "WG-DOCS",
      "title": "更新使用文档",
      "status": "进行中",
      "next": "核对说明与当前实现",
      "summary": "补充工作记录配置和数据边界。",
      "commits": []
    },
    {
      "id": "WG-DOCS-SCOPE",
      "parentId": "WG-DOCS",
      "kind": "outcome",
      "title": "明确工作记录的数据边界",
      "status": "已完成",
      "summary": "已写明读取范围与归属规则，尚未由用户验收。",
      "outcomes": ["说明 HEAD 历史的读取范围"],
      "issues": ["后续需随实现核对"],
      "commits": []
    }
  ]
}
```

| 字段 | 要求 |
| --- | --- |
| `version` | 必须为数字 `1` |
| `works` | 必填数组，父项和子项合计最多 100 个，可为空 |
| `id` | 唯一标识，1–40 个字符，以大写英文字母开头，其余只能是大写英文字母、数字或连字符 |
| `title` | 必填非空白字符串，最多 160 个字符 |
| `status` | 必须是 `进行中`、`已完成`、`已搁置`、`待开始` 之一 |
| `commits` | 必填数组，可为空，单项最多 1000 个；填写完整提交 SHA，同一 SHA 不能重复填写或分配给多个工作项 |
| `next`、`summary` | 可选字符串，各最多 1000 个字符 |
| `parentId` | 可选，填写已有工作项 ID；省略时为顶层动线。拒绝缺失父项、循环引用，最多支持三层 |
| `kind` | 可选，`work`（默认）为工作，`outcome` 为成果；只改变展示类型，不证明完成或验收 |
| `updatedAt` | 可选，实际维护记录时填写 UTC ISO 时间，如 `2026-10-28T08:00:00.000Z`，也接受不带毫秒的形式；界面按北京时间展示，缺失显示 `—`，不使用提交时间补齐 |
| `outcomes`、`issues` | 可选字符串数组，各最多 20 项；每项非空白且最多 1000 个字符，分别记录成果与问题／边界 |

文件必须是普通文件，不能是符号链接，大小不能超过 256 KiB。格式错误会阻止工作视图加载。不要使用 `UNASSIGNED` 作为自定义工作项 ID；它用于显示未关联的提交。

以上可选字段扩展现有 `version: 1`；旧的平面工作记录仍可读取。工作项拒绝未知字段。子工作应依据明确目标与完成条件整理，不能仅为形成树状结构创建记录，也不能因子项完成就自动修改父项状态。

建议将记录与代码一起提交。界面读取当前工作区的文件，尚未提交的记录修改也会在刷新后显示。不同 Worktree 读取各自工作区的记录；裸仓库不读取此文件。

## 关联提交

关联方式有两种：工作记录中的完整提交 SHA，以及提交正文中的 `Work-Item: WG-ID` 标识。显式 SHA 优先；没有明确关联的提交归入「未关联的提交」。未提交文件单独显示，不推断工作归属。历史重写后需要核对并更新 SHA；本版不自动修复关联。

父项详情可以汇总后代的明确关联，并标注来自哪个子项；子项不会继承父项提交。父项已有提交无需强行重新分配给子项。没有单独关联时，子项「代码依据」明确显示暂无关联。

例如，为上面的 `WG-DOCS` 工作项创建提交时，可在提交消息正文中另起一行写入 `Work-Item: WG-DOCS`。没有显式 SHA 关联时，正文中必须恰好有一行符合格式的标识，且 ID 已存在于工作记录中；多个标识或未知 ID 都不会建立归属。仅在提交标题中写入标识不会生效。

## 数据范围与限制

工作轨道表示同一工作的成果归属，不表示 Git 父子关系。历史提交的工作归类依据本次整理，Git 日期与差异来自仓库事实。工作记录和代码一起提交，其他仓库未配置记录时只显示未关联历史。

本版只读取当前 HEAD 可达历史，超过 300 条时提示截断；其他分支和 worktree 的完整历史仍在 Git 模式查看。自动维护仅在本地服务运行期间检测代码变化，没有实现常驻系统服务、自动提交、恢复点或自动验收。界面读取失败会显示错误，不回退到演示数据。
