# WorkGraph 本地版与云端版设计

设计日期：2026-11-09。状态：产品方向已确认，实施方案待实现。本文统一维护共用工作模型、两种运行形态的边界及实施顺序；不代表已经提供云端服务或跨分支工作汇总。

当前实现与存储格式分别以[架构与安全边界](current-implementation.md)和[工作记录与数据边界](work-graph.md)为准。本文中的概念字段不是现有 `state.json` 的可写字段，实施前需要定义版本化契约与迁移规则。

## 产品目标

工作进展图应解释整个仓库有哪些工作在推进、分别进展到哪里、哪些成果进入了目标分支，以及哪些问题需要关注。图以目标、工作和成果组织；分支、提交、PR 和检查结果提供依据。一个工作可以关联多个分支，一个分支也可以承载多个工作。

产品提供两种可以独立使用的运行形态：本地版支持个人在自己的机器上维护工作进展；云端版面向多人协作和大型仓库，维护团队共享的仓库视图。本地版不要求云端账号或连接；云端版不要求每个开发者运行本地版。

「整个仓库」指已声明观察范围内的仓库信息，不意味着掌握所有人的工作。两种形态都必须显示覆盖范围、观察时间、失败和截断信息。

## 共用工作模型

### 工作身份与关系

| 概念 | 约束与用途 |
| --- | --- |
| 仓库身份 | 使用稳定身份关联数据，远程 URL 和目录路径作为可变化的定位信息；GitHub 适配器应保留平台仓库身份 |
| 工作 ID | 在仓库内稳定且唯一，不由分支名、目录名或聊天 ID 推导；重命名、合并和删除分支不删除工作 |
| 目标、工作、成果 | 以父子关系组织；先沿用现有层级表达，独立目标类型不是首阶段前提 |
| 工作关联 | 关联分支、提交、PR、Issue、验证记录；保存明确关联与推断关联的区别 |
| 来源与版本 | 保存来源对象、来源版本或 SHA、观察时间、记录者类别及更新版本，支持追溯和过期判断 |

相同工作 ID 在多个分支上的记录是同一工作的不同来源，不能按更新时间直接覆盖。独立创建的同名工作不自动合并；ID 冲突需要核对、重映射并保留原关联。

### 状态分开表达

| 维度 | 要回答的问题 | 判定边界 |
| --- | --- | --- |
| 工作进度 | 待开始、进行中、阻塞、搁置或实现完成 | 来自明确记录或带依据的分析，不能由提交数量决定 |
| 验证情况 | 哪个版本执行了什么检查，结果如何 | 结果绑定 SHA、检查范围及时间；旧版本通过不代表新版本通过 |
| 集成情况 | 哪些成果已进入哪个目标分支 | 必须指定目标分支，允许部分合入、尚未合入与待核对 |
| 验收情况 | 谁确认了哪些完成条件 | 没有明确验收记录时保持未知，不从合并或测试通过推断 |

这些是目标语义，不替换当前版本的状态枚举。旧记录中的「已完成」迁移后仍保留原意，不补造验证和验收结论。

Git 可达性支持普通合并的判断；Squash merge、Cherry-pick 和历史重写需要结合平台关联及其他证据核对。不能仅因原 SHA 不可达就判断未合入，也不能把补丁相似当作已经验收。

### 事实、人工记录与分析判断

平台或 Git 事实、人工确认记录、Agent 推断分别保存。事实描述观察到的对象状态；人工记录负责目标、完成条件、负责人、阻塞与纠正；分析判断负责候选归类、摘要和证据解释。

人工确认字段不被后续分析静默覆盖。不同来源有冲突时保留来源和差异，标记待核对；过期证据不删除，但不继续当作当前结论。父项可以汇总子项成果，不因子项完成而自动宣告父项完成。

## 本地版边界

目标范围为本地分支、已获取的远程引用、可访问的 Worktree，以及各工作区未提交的变化。无须切换分支即可从 Git 对象读取已提交记录；各 Worktree 的未提交记录分别读取。本地分支与对应远程引用归并展示，同时保留它们的差异。

工作记录继续允许随代码提交，各 Worktree 保留自己的记录。增加仓库级聚合视图，聚合缓存可以放在 Git 共用目录，缓存可重建，不取代原记录。未提交修改按工作区展示，没有明确关联时不归属某个工作。

本地分析保持用户主动触发。刷新读取数据，不隐式调用模型；远程同步属于明确操作，界面显示最近获取时间。网络不可用时仍可使用本地信息。现有 Git 写操作沿用独立的审阅和执行边界，不因工作状态变化自动提交、合并或推送。

当前「工作进展」仍是当前工作区及 HEAD 历史视图。本节的全分支聚合属于后续实施范围，不能把 Git 历史已经支持多分支等同于工作进展已经支持仓库汇总。

## 云端版边界

云端维护团队共享的工作记录与发布快照。观察范围包括授权可见的远程分支、PR、Issue、提交、检查结果和已发布的工作记录；不包括开发者未推送的代码、私有聊天或未主动发布的本地记录。其他仓库中的 PR 源分支需要单独记录可见性，无法读取时显示覆盖缺口。

CI 承担采集与分析任务，集中存储承担持久状态与版本管理，Web 页面读取已发布快照。CI 工作目录和短期运行产物不能成为工作记录的唯一保存位置。事件日志和历史快照用于追溯；可重建的摘要与缓存不拥有人工记录。

初期 Web 页面只读，展示仓库概览、工作图、近期成果、待评审或被阻塞的工作，以及同步范围和时间。详情链接到原始证据。长期无活动只标记为近期无活动，不自动判定放弃；分支删除后保留工作及成果。

### 更新与发布

1. 事件触发后重新读取相关对象的当前状态，不把到达顺序当成业务顺序。
2. 按仓库和来源版本去重，仅分析受影响工作。定期核对引用和对象清单，补足遗漏事件。
3. 候选更新绑定读取时的状态版本；集中端校验后原子发布新快照。旧任务不能覆盖新版本，冲突时重新收集材料。
4. 采集或分析失败保留上一份有效快照，并显示失败来源和过期范围。部分来源失败不能显示为「没有工作」。

大型仓库采用有界首次扫描、增量游标、按对象版本缓存、任务合并和可恢复重试。扫描窗口、并发和模型预算可配置，达到预算时记录未覆盖范围；不要求每次事件遍历全仓库或调用模型。定期完整核对指核对配置范围内的对象清单，不意味着无限扫描全部历史。

### 权限与执行隔离

云端读取权限和快照发布权限分离；页面及数据的可见性不得扩大源仓库权限。私有源码、差异、提示词和凭据不进入公开构建产物。模型可读取的材料范围与保留策略需要明确配置。

PR 文本和仓库内容都是待分析数据，不作为执行指令。在持有发布凭据或模型密钥的任务中，不执行不受信任分支提供的脚本；受信任采集与发布代码使用独立边界。工作进展服务消费已有检查结果，不替代项目 CI，也不自动执行代码合并或验收。

## GitHub 首个试点

试点仓库为 `Daoming-Chen/codex-work-graph`，目标分支先配置为 `main`。这是当前仓库的实施示例，不假定已启用云端部署、具备所需凭据或已选择公开站点。

建议由 GitHub Actions 执行初期采集任务，集中保存版本化快照与人工记录，Web 页面读取已发布版本。具体事件配置、凭据方式、持久存储和托管产品在云端试点实施前核实并确定；本文不提供可直接部署的工作流。

| 变化 | WorkGraph 预期反应 |
| --- | --- |
| 功能分支推送 | 更新分支观察与提交依据，提出工作关联候选 |
| PR 创建或更新 | 关联源分支和目标分支，整理范围；评审状态与工作进度分开 |
| 检查完成 | 将检查结果绑定实际检查的版本，不沿用旧版本结论 |
| PR 合并到 `main` | 核对并更新相关成果的集成情况，保留原分支和 PR 来源 |
| 分支删除或强制推送 | 更新引用及证据有效性，保留历史工作，不按提交缺失删除成果 |
| 定期核对 | 发现漏处理事件、删除对象、不可访问来源和过期快照 |

试点验收使用一项明确标为示例的工作，覆盖「分支推送 → PR → 检查 → 合并 → 删除分支」。同时模拟检查失败、重复和乱序事件、旧分析晚完成、Squash merge、采集权限不足。示例不使用虚构 PR 编号或把假定事件写成仓库现状。

## 本地与云端的可选连接

本地可读取云端快照作为团队基线，再叠加自己的工作区观察；页面区分团队共享进展与本地未发布变化。用户可主动发布指定工作的目标、进展和阻塞，默认不上传未提交代码及聊天内容。

连接时使用仓库身份、稳定工作 ID 和基线版本。发布的是带来源的更新请求，不是全量文件覆盖；云端冲突返回本地核对，断网时保留待发布状态。不得把旧云端快照写回并覆盖本地记录。未启用连接时，两种形态各自正常工作。

## 分阶段实施方案

下列阶段均未交付。本表是本文的实施顺序与交付状态唯一入口；实施后更新本表，并同步当前实现文档，不把规划描述直接当作已实现接口。

| 阶段 | 交付范围 | 完成标准 |
| --- | --- | --- |
| 0：共用模型与兼容契约 | 定义身份、来源、状态维度、更新版本和快照协议；设计旧记录适配及迁移 | 旧数据可读取；无证据时不生成验证或验收结论；覆盖 ID 冲突、多来源差异及往返序列化 |
| 1：本地仓库聚合 | 读取多个分支和 Worktree，增加工作级聚合与覆盖提示；保留当前使用入口 | 两条未合并分支的工作均可见；相同工作可汇总；未提交变化可区分；分支切换不丢记录；离线可用 |
| 2：GitHub 只读云端试点 | 在当前仓库接入事件采集、集中持久快照、受控发布和只读 Web；先支持明确关联，再提供分析候选 | 跑通试点事件流程；任何一次发布可追溯；失败保留有效版本；并发任务不能倒退状态；页面不暴露超出授权范围的数据 |
| 3：团队维护与大型仓库运行 | 人工修正、负责人、阻塞和验收记录；审计、队列、预算、增量恢复、备份恢复 | 人工确认不被模型覆盖；重复及乱序事件结果一致；任务可恢复；用约定规模样本记录耗时、费用和覆盖率，达到实施前确定的预算 |
| 4：可选本地连接 | 团队基线读取、本地叠加、选择性发布和冲突处理 | 两种形态仍可独立使用；断网不丢更新；未授权材料不上传；同一工作不重复创建，冲突不静默覆盖 |

阶段 0 是后续阶段的共同前提。阶段 1 与阶段 2 可以在契约稳定后分别推进，云端试点不以本地全量功能交付为前提。阶段 3 基于阶段 2 的运行证据扩展；阶段 4 在两端身份与更新协议稳定后实施。

首轮不包含跨仓库项目汇总、自动合并、自动验收、自动上传本地材料或公网暴露现有本地服务。云端部署需新增受控入口，不能直接复用本地回环服务的信任假设。

### 实施前需要确定的配置

- 阶段 0：最终存储版本、旧记录兼容方式和人工确认字段的更新权限。
- 阶段 2：GitHub 授权方式、模型调用配置、站点访问范围、持久存储及快照保留策略。
- 阶段 3：代表性仓库规模、刷新目标、费用预算与失败恢复目标。先测量后确定数值，不在设计中承诺未经验证的性能。
